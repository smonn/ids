# Opaque Timestamp key rotation is caller-driven (forward-only), not transparent

The Opaque Timestamp codec's AES-CBC payload is **unauthenticated** ([ADR-0004](./0004-aes-cbc-strip-trick.md): a wrong key never throws and never yields a padding oracle — the strip-trick reconstruction always produces valid PKCS#7, so a wrong key yields a plausible-looking timestamp, not an error) and **wire-indistinguishable with no key id** ([ADR-0007](./0007-wire-indistinguishable-codec-variants.md): no version marker on the wire). There is nothing to match a key against and nothing to validate a trial-decrypt guess. The codec therefore offers **no transparent "try every key in a ring" rotation**, and does not gain a keyring API.

Rotation is **forward-only and caller-driven**. The key feeds only `generate` and `extractTimestamp`; `parse`, `safeParse`, `is`, and `toJsonSchema` work on the wire form and never touch it. So rotating forward is nearly free: new IDs encrypt under a new key, old IDs stay valid opaque strings whose _timestamp_ simply becomes unreadable without the old key. An operator holds **one codec instance per [key epoch](../../CONTEXT.md)** and selects the instance to read an ID's timestamp from its own out-of-band record of which epoch minted that ID. No wire change, no API change.

This is the design-acceptance gate for issue [#103](https://github.com/smonn/ids/issues/103). Because the accepted approach needs no implementation (see Consequences), the design acceptance and its documentation land together; there is no separate implementation follow-up issue.

## Considered options

- **Forward-only, caller-tracked — ACCEPTED.** `generate` encrypts under the single key its codec instance holds; `extractTimestamp` requires that same key. The caller records each ID's epoch out-of-band and picks the matching codec instance. Honest about what an unauthenticated, unversioned wire can support: nothing about the ID tells you which key produced it, so the caller — who minted it — must remember.

- **Probabilistic trial-decrypt — REJECTED (not shipped).** Try each candidate key and accept the one whose decoded 48-bit timestamp lands in a plausible window. The 48-bit millisecond field spans ≈ 2⁴⁸ ms ≈ 8920 years; against a ~10-year plausibility window, a **stale key false-accepts at ≈ 10 / 8920 ≈ 0.11% per stale key tried**. That is **dashboard-grade, never correctness-grade**. We will not ship it as a built-in: a library method that returns a "probably right" timestamp structurally mimics transparent rotation while being a guess, and invites callers to trust the guess as ground truth. An operator who genuinely wants a best-effort reading can build it in a few lines over the public `extractTimestamp` plus their own plausibility check — at their own risk — without the library blessing it.

- **Transparent try-all-keys — REJECTED here, DEFERRED to the Signed Timestamp codec.** A correctness-grade ring needs something to verify a decrypt against. The Opaque codec has no tag. The **Signed Timestamp codec** ([ADR-0012](./0012-signed-timestamp-construction.md), issue [#100](https://github.com/smonn/ids/issues/100)) does: its truncated-HMAC tail gives a **Signing keyring** whose `verify` trials the ring by tag match, which _is_ correctness-grade. Callers who need transparent, correctness-grade rotation of a readable-and-verifiable timestamp use that codec instead. The Opaque codec trades verifiability away for confidentiality; that trade is the point, not an oversight.

- **Wire key id on the Opaque codec — REJECTED.** Same reasoning that rejected GCM in [ADR-0004](./0004-aes-cbc-strip-trick.md): a key id either eats the 80-bit random budget or breaks the 16-byte / strip-trick invariant, and a version marker reintroduces exactly the wire distinguishability [ADR-0007](./0007-wire-indistinguishable-codec-variants.md) removed. This is the cross-cutting rejection — no option on the table adds a key id to the wire.

## Why no keyring API on this codec

Even forward-only rotation _could_ be expressed as `createOpaqueTimestampId(brand, { keys: [OpaqueKey, ...] })` with an explicit epoch hint on `extractTimestamp`. We reject that surface deliberately.

A `keys` array structurally implies the library manages a ring for you — the exact transparent-rotation promise this codec cannot keep. Keeping the codec **single-key** makes the honesty legible in the type: one instance, one key, and "caller-tracked" means the caller literally holds the instances (e.g. a `Map<epoch, OpaqueTimestampCodec>`). It also keeps `extractTimestamp(id)` arity-stable — **no breaking change** — and reserves the keyring vocabulary for the codecs where trial is correctness-grade: the **Wrapping keyring** ([ADR-0009](./0009-wrapped-key-compact-construction.md)) and the **Signing keyring** ([ADR-0012](./0012-signed-timestamp-construction.md)).

## Consequences

- **No code change.** Single key per codec instance, exactly as today. The rotation pattern is a caller-held `Map<epoch, OpaqueTimestampCodec>`: `generate` on the current instance, `extractTimestamp` on whichever instance matches the ID's recorded epoch.
- **The epoch cannot come from the ID.** Opaque IDs are wire-indistinguishable and their timestamp is unreadable without the key, so the caller cannot derive an ID's epoch from the ID itself. It must come from an external record — a key-epoch column, a tenant→key map, a created-at cutover. This is the load-bearing constraint of the whole approach; without it there is no rotation story, only a single immutable key.
- **Multiple instances per brand trip the dev warning, by design.** Holding more than one codec for a brand fires the brand registry's non-production `console.warn` ([ADR-0007](./0007-wire-indistinguishable-codec-variants.md)). Rotation is precisely the "isolated codec instances bundled together" case that warning's `allowDuplicateBrand: true` opt-out exists for, so the non-current instances pass `allowDuplicateBrand: true`.
- **The CLI follows the same rule.** `inspect --opaque` reads a single `IDS_KEY`; reading an old-epoch ID means re-running with that epoch's key in `IDS_KEY`. There is no CLI-side ring.
- **New vocabulary.** A **Key epoch** entry lands in `CONTEXT.md`; the **Opaque key** entry gains a rotation pointer; the "Wrong Opaque key is indistinguishable from the right one at decrypt time" gap note is resolved by pointing here.
- **Does not reopen closed decisions.** This depends on [ADR-0004](./0004-aes-cbc-strip-trick.md) (unauthenticated strip-trick) and [ADR-0007](./0007-wire-indistinguishable-codec-variants.md) (wire-indistinguishable variants) rather than revisiting them — they are the reason transparent rotation is impossible here, not obstacles to work around.
