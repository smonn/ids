## Open findings (ranked, grouped as filing units)

1. **Low (security-hardening) — the source-hygiene invisible-byte detector misses DEL (U+007F) and part of the Unicode bidi/format block.** `.github/scripts/source-hygiene-lint.mjs:29`: `FORBIDDEN_RE` bans C0/C1 controls, the Trojan-Source bidi set (U+202A–U+202E), zero-width/format chars (U+200B–U+200F, U+2060–U+2069) and BOM, but leaves gaps inconsistent with the file's own stated intent ("NUL, C0/C1 controls, bidi/format chars"): **DEL U+007F** sits in the uncovered gap between the `\u000e-\u001f` and `\u0080-\u009f` ranges (`FORBIDDEN_RE.test("\u007f") === false`), and the Arabic Letter Mark **U+061C** plus the deprecated format controls **U+206A–U+206F** are uncovered. The header comment lists only tab/LF/CR as deliberate exclusions, so these read as oversights, not policy. Exploitability is lower than the covered RLO/LRO overrides (DEL/ALM/deprecated-format do not force a strong visual reorder — the CVE-2021-42574 primary vector stays covered), so this is hardening, not a live bypass — but a raw U+007F can still hide/obfuscate a diff hunk in most editors/blame views, exactly the "unreviewable by diff/grep/blame" hazard the detector exists to stop. Surfaced while auditing finding-5's new `checkContent`/`lintFiles` harness (unchanged code; the diff only added tests around it). **Direction:** extend the class to `\u007f` (DEL), `\u2060`–`\u206f` (widening the existing `\u2060-\u2069`), and `\u061c` (or document the narrower intent), with regression cases added to the new `checkContent` unit tests. Class-level AC: one probe per newly-banned code point, mirroring the existing per-disjunct test structure. **Disposition: file (ready-agent, low-priority).**

2. **Low (docs) — the 1.2.4 empty-hex erratum over-narrows the `decode*Key` → `invalid_key_length` trigger.** `website/src/content/docs/errors.md:78`: the `invalid_key_length` row opens correctly ("Raw key bytes are not 16, 24, or 32 bytes") but the clause added by #1056 narrows the `decode*Key` case to "yields **fewer than 16 bytes** (e.g. an empty hex string `""` decodes to 0 bytes)." A hex/base64url string that decodes successfully to 20, 28, or 40 bytes also throws `invalid_key_length` via the same length assert, and none of those are "fewer than 16." A consumer reading only the elaborating clause could build incomplete handling (assuming any non-empty, reasonable-length decoded key is safe from this code). The `""` example is correct; only the general framing is imprecise. **Direction:** reword to "…decodes successfully but yields a byte length not in {16, 24, 32} (e.g. an empty hex string `""` decodes to 0 bytes)." Single-file doc fix. **Disposition: file (ready-agent, low-priority).**
