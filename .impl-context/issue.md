# enhancement: enforce the 3-character brand constraint at the type level

> *Filed by an AI repo audit (API/DX agent).*

## Agent Brief

**Category:** enhancement
**Summary:** The runtime requires brands to be exactly 3 characters, but the `Id<Brand>` generic accepts any string, so an invalid brand only fails at runtime with no compile-time signal.

**Current behavior:**
Codec constructors validate brand length at runtime, but `Id<Brand>`/the constructor generics accept arbitrary `string`. A consumer can write a 2- or 4-char brand and get no type error — the failure surfaces only when the code runs.

**Desired behavior:**
A brand that is not 3 characters is rejected (or at minimum strongly discouraged) at the type level, so the mistake is caught at compile time. If a fully-precise 3-char string type proves too hostile to inference, provide a constrained helper type and document the limitation.

**Key interfaces:**
- The brand type parameter on `Id<Brand>` and the codec constructors — add a length constraint or a branded `Brand` helper type.

**Acceptance criteria:**
- [ ] A non-3-character brand produces a `pnpm typecheck` error (or a clearly-documented constrained-type alternative).
- [ ] Valid 3-char brands still infer correctly with no extra annotation at call sites.
- [ ] Existing tests/usages compile unchanged.

**Out of scope:**
- The `unique symbol` brand change (#470) — this builds on it.

## Analysis

The unique-symbol brand change hardened `Id<Brand>` against structural spoofing, but all public codec constructors still declare `Brand extends string`. A caller can pass a 1-, 2-, or 4+-character brand and receive no compile-time diagnostic — the failure surfaces only at runtime via `validateBrand`.

**Redundancy check:** No type-level brand-length constraint exists anywhere in the codebase. The `brandPattern = /^[a-z]{3}$/` regex in the `validateBrand` function is runtime-only.

**Prior rejection check:** ADR-0001 closes the _format_ decision (3 chars, lowercase a–z), not the question of whether to enforce it at the type level. This issue adds a new enforcement surface on top of a closed decision — it does not reopen the format itself.

## Agent Brief

**Category:** enhancement
**Summary:** Add a `ValidBrand` template-literal type and tighten all public `Brand extends string` constraints to `Brand extends ValidBrand`, so passing a non-3-char brand is a compile-time error.

**Current behavior:**
All codec factory functions (`createTimestampId`, `createOpaqueTimestampId`, `createReverseTimestampId`, `createSignedTimestampId`, `createWrappedKeyId`, `createDigestId`) and the `Id<Brand>` / `Prefix<Brand>` types in `types.ts` accept `Brand extends string`. A caller can write `createTimestampId("ab")` or `createTimestampId("user")` and see no TypeScript error; the failure is deferred to runtime.

**Desired behavior:**
A `ValidBrand` type — defined as a template-literal union over all 17,576 three-lowercase-letter strings — replaces `string` as the upper bound on every public `Brand` type parameter. Passing a brand that is not exactly three lowercase a–z characters produces a `pnpm typecheck` error at the call site. Passing a valid brand such as `"usr"` continues to infer `Brand = "usr"` with no extra annotation required.

**Key interfaces:**
- `ValidBrand` — new exported type in `types.ts`; defined as `` `${BrandChar}${BrandChar}${BrandChar}` `` where `BrandChar = 'a' | 'b' | ... | 'z'`. Export it so callers can annotate their own helpers.
- `Id<Brand>` and `Prefix<Brand>` in `types.ts` — tighten constraint from `Brand extends string` to `Brand extends ValidBrand`.
- Every codec type alias (`TimestampCodec<Brand>`, `OpaqueTimestampCodec<Brand>`, `ReverseTimestampCodec<Brand>`, `SignedTimestampCodec<Brand>`, `WrappedKeyCodec<Brand>`, `DigestCodec<Brand>`) — same tightening.
- Every codec factory function signature — same tightening on the `Brand` type parameter.
- Internal helper types (e.g. `ParseResult<Brand>`, `StandardSchemaProps<Brand>`) — tighten where they appear in public API surface; leave internal-only types alone to avoid cascade noise.

**Acceptance criteria:**
- [ ] `ValidBrand` is exported from the main entry point and resolves to the 17,576-member template-literal union.
- [ ] `createTimestampId("ab")`, `createTimestampId("user")`, and `createTimestampId("123")` each produce a `pnpm typecheck` error at the call site.
- [ ] `createTimestampId("usr")` infers `Brand = "usr"` without requiring an explicit type argument.
- [ ] All existing tests and usages (`"usr"`, `"opc"`, `"zbc"`, `"zbd"`, etc.) pass `pnpm typecheck` and `pnpm test` unchanged.
- [ ] If the 17,576-member union causes a measurable regression in `pnpm typecheck` wall-clock time (compare before/after), document the trade-off in a comment on the `ValidBrand` type and consider the constrained-helper alternative described in the original issue body; the triage caller will review.

**Non-goals / Out of scope:**
- Changing the 3-char brand format itself (closed in ADR-0001).
- Runtime validation changes — `validateBrand` stays unchanged.
- Enforcing the constraint on the internal `_kernel` layer (internal-only paths may keep `Brand extends string` to avoid noise; the public API surface is the target).
- Adding a new error code or modifying `IdsError` (the `invalid_brand` runtime error is unchanged).
- Any change to `.github/workflows/` files.
